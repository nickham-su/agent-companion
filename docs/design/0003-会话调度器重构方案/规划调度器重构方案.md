# 会话调度器重构方案

本方案面向 `v0.1`。调度器统一接收会话输入并决定何时放行。Runtime 继续负责入队后的串行执行、工具续轮和安全边界。通道层根据实际连接选择回复方式，并处理语音播放、停播和投递结果。

## 每个会话一个调度器

- 调度器是按会话 ID 归属的组件，由应用的内存映射表管理。主会话和子会话共用 Runtime 的输入和输出接口。会话记录和历史按需查库。
- 调度器创建时绑定模型输出的投递实现。主会话的输出目标是用户，由面向用户的投递实现交给通道层。子会话的输出目标是父会话，由面向会话的投递实现把完整任务结果作为新输入交给父会话调度器。

### 实例创建

有效的新事件需要调度器处理时，统一投递入口按会话 ID 查表，有实例就复用，没有就创建并登记。查找与登记作为同一步完成，同一会话同时只使用一个实例。飞书消息、子任务回投和确认接通的通话都可以触发创建。

调度器首次创建后在应用进程内常驻；挂断或 Runtime 回到空闲都不回收实例。`v0.1` 不做回收与重建，也不需要监听 Runtime 的启停来管理实例。

## 会话事件

事件名统一用小写字母和下划线。

| 事件名 | 触发时点和用途 |
| --- | --- |
| `session_input` | 会话收到消息内容、输入状态变化，或同时收到两者。由调度器处理。 |
| `call_started` | 通道层确认通话接通并装好语音回复路由，提交 `通话已接通 - <日期时间>`，标记为 `trigger`。 |
| `call_ended` | 已接通的通话结束，提交 `通话已结束 - <日期时间>`，标记为 `record`；解除当前通话输入状态时，先追加消息再按规则整批放行。未接通的清理不生成消息。 |

回复对象和最终回执沿投递接口交接。

两条通话状态消息使用事件发生时的时间，经 `session_input` 走普通队列，不为接通加固定问候、优先级或专用唤醒。生命周期消息即使迟到也按到达顺序提交，不借它改变其他通话的输入状态。普通和压缩请求都允许这些 `state_event` 进入上下文；历史只存正文，适配器以 `user` 消息加上 `[状态事件]` 前缀。`record` 只表示不单独启动模型，同批或后续请求仍能看到。

## 输入状态和放行

用户输入、子任务回投和其他外部会话消息都先进入目标会话的调度器。主会话调度器保存语音层提供的「输入中／空闲」状态和待放行的消息。用户开口、等待话轮结束和等待转写都属于「输入中」。语音层确认所有实时话轮都已结束后，报告「空闲」。已解绑的通话迟到的「输入中／空闲」信号或转写不再接收，也不能影响后续通话。

`session_input` 可以携带内容、状态变化，或同时携带两者。调度器按会话串行处理事件，把接收内容、更新状态和决定是否交接作为同一步完成。处理后处于「空闲」且队列有消息时，交接一个批次。处于「输入中」时，消息继续暂存。

- **只带内容。** 用户正在说话时补发飞书文字或图片，这些内容进入调度器的待放行队列，语音输入状态保持「输入中」。这期间到达的子任务结果同样暂存。
- **同时带内容和状态变化。** 最后一个待结束的语音话轮有有效转写时，语音层在同一事件中交付转写文本和切到「空闲」的信号。调度器先把转写追加到队尾，再切换状态，把待放行消息作为一个批次交给 Runtime，不因这次状态切换而把转写与已暂存的消息拆开。
- **只带状态变化。** 语音层可以在确认开口时报告「输入中」，也可以在空转写、失败或超时收尾后报告「空闲」。切到「空闲」时，有待放行消息就整批交给 Runtime。队列为空时保持空闲。

入站方在暂存前将消息封装为 `MessageDelivery`，标记 `trigger` 或 `record`。标记与消息独立，不写进消息或数据库。调度器只决定何时放行，不重判标记，也不按标记拆批、按来源重排或区分优先级。子会话的任务通过原有准入后，由子会话调度器直接放行。

飞书图片在投递前保存至对应用户工作区的 `.agent/images/`，暂存和历史都只携带相对引用。Runtime 为普通请求和压缩请求各自选定上下文后再加载图片；文件读写和编码共用有界的图片专用线程池，不占用语音的默认池；取消排队不启动 I/O，已开始的任务结束后才释放额度。普通请求先分配当前运行受保护的图片预算，再分配旧图，投影顺序不变。准备阶段也受请求截止和取消约束，失效的请求不发给适配器。

### 异步工具结果

每次工具调用只对应一条工具结果；异步工具也必须立即返回这条结果，例如「已受理」。异步结果作为新消息另行投递。子 Agent 每次运行结束后沿已绑定的直属父级路由回投本轮正文或失败原因，不绑定原通话或原工具调用，不等待整个委派任务完成。

回投转换成一条标记 `trigger` 的消息，调度器按同一套规则暂存和放行。父级 Runtime 直接接收并写入新 `async_tool_result` 消息，不查库核验子运行终态、比对内容或去重。模型适配器以 `user` 消息携带异步结果通知，不为原调用追加第二条工具结果。

## Runtime 入队、执行与输出

调度器一次放行的原序数组通过唯一消息入口 `submit_messages(deliveries)` 整批加入 Runtime 的 FIFO。入队不表示立即执行。Runtime 在现有安全点原子写完队首，确认后才出队。提交结果不确定时不重放。

工具已结算且允许运行续轮时，已入队的消息可纳入当前 `run_id`；没有新消息也照常续轮。纯文本答完先结束旧运行，之后每批有至少一条实际写入的 `trigger` 才新开运行，只有 `record` 时只写历史。新运行的上下文保护从同批第一条实际写入的消息开始，不因最早的消息是 `record` 而跳过。两种标记都走相同的队列和模型清理等待。

飞书在通道侧保留水位、去重、恢复和原始批次。非空批次先准备媒体、绑定用户会话，确认原始批次后立即同步提交消息；空批仅确认。SQLite 暂锁时只重试失败步骤，不重做已整理媒体。确认原始批次的提交结果未知时，安全回滚后只核验相应用户和批次；能证实已删除才继续交接，其余情况暂停该用户的原始批次交接，不重试确认。未确认的原始批次支持重启后继续处理；已确认但尚未写入会话历史的内存消息可能丢失。通话空转写的无消息唤醒仍是单独的 `trigger_run`；它让位于该用户尚未确认的原始批次及调度器、Runtime 两处待写消息，准备图片后、首个模型请求派发前复核资格。

Runtime 通过本会话的调度器交付模型文本。纯文本回复与同一模型响应中伴随工具调用的文本共用输出接口，工具调用及其结果仍由 Runtime 处理。

- **主会话面向用户的输出。** 统一以回复流进入投递接口。通道层在回复交接时选择实际投递方式和对应的确认语义。
- **子会话面向父会话的输出。** 固定按全文交付。Runtime 写入子会话历史并确认本轮终态后，将本轮完整正文或失败原因回投给直属父会话。一次委派可以收到多次运行的回投。父会话再向用户回复时，按自身的用户投递规则处理。

Runtime 交付流式回复或全文时，底层模型均可沿用现有的流式调用。

## 通道选择和文字交接回执

通道层维护接通状态，每条回复在首次交接时按用户的实际连接选择一次通道。电话接通时，即使本轮输入来自飞书补充材料或子任务结果，生成的回复也可以在当前电话里流式播报。交接时没有有效通话（例如先挂断、后产生回复），就走飞书全文发送。

- **语音交付。** 通道边收边播。回复一旦交给语音层，随后即使挂断也不改发文字，按原通话回执确认的已播前缀结算；尚未播出时为零投递。
- **全文交付。** 飞书文字投递端收齐全文后返回「已收齐」的交接回执。Runtime 确认模型响应完整并完成历史提交后，通道将全文交给后台发送队列。飞书 CLI 的实际发送结果由通道层结算。CLI 超时表示结果未知，Runtime 可以继续处理后续输入。

接通状态的读取方式和全文落库后的发送通知在实施前确认。全文交付可以复用 Runtime 已收集的正文。

## 流式回复和播放回执

Runtime 写入 `ReplyStream`，调度器在放行时把同一个对象交给实时语音层读取和播放。语音层仍通过该对象提供播放进度。调度器拦截和语音层结束播放都复用 `deliver(reply) -> Receipt` 返回唯一的最终回执。不在流对象上另存一份回执，也不另发停止模型流的通知。

## 两处打断和历史结算

- **交给实时语音层之前。** 调度器准备转发语音回复时，如果用户已处于「输入中」，直接返回零投递（`ZERO`）。已因用户开口而过期的回复，不因转写结束而恢复播报。
- **交给实时语音层之后。** 语音层检测到用户开口时，沿用现有的停播机制，清理待播内容，返回已确认的播放前缀（`PARTIAL`）；没有确认到正文则返回 `ZERO`。

Runtime 读取模型流的同时监听最终回执，不等模型流结束才取回执。收到非完整的语音流式投递回执（状态不是 `FULL`）时，Runtime 立即截断仍在进行的模型流，不再启动本轮的新工具；已经启动的工具照常完成，工具调用和对应结果与回执确认的正文一同落库。即使模型流已经结束，本轮也在结算后结束，不再进入工具续轮。

这里只结束本轮，不关闭 Runtime；队列后续批次的有效 `trigger` 可开启新运行，不额外等待语音输入结束。尚未交接的输入仍由调度器控制放行。纯工具轮没有投递回执，照常推进；飞书后台发送结果不触发这条规则。

纯文本回复零投递时，模型可见的历史略过该空回复。非完整投递只保留回执确认的正文前缀。带工具调用的回复即使正文为空，工具调用和对应结果也完整保留。下一轮使用已有上下文和新输入，正文里不追加打断标记，也不另设待汇报标记。

## 验证场景

- 同一会话首次同时收到多个事件时只创建一个调度器。Runtime 空闲或通话挂断后，新的消息和子任务结果仍复用原实例。
- 异步工具调用即时收到唯一的工具结果；之后的回投作为独立消息进入 FIFO，不带原调用 ID，不增加第二条 `tool` 消息。
- 用户说话时先收到飞书消息，再收到子任务结果，最后收到有效转写与「空闲」。调度器只交接一次批次，顺序为飞书消息、子任务结果、转写。空转写、失败或超时也能放行已暂存的消息。
- Runtime 正处于工具执行或续轮时收到已放行输入，仍在原有安全边界处理。同一会话串行，子任务按原有准入规则推进。
- 确认接通后即可由状态事件触发请求；飞书补充材料触发的回复也可在电话里播报。交给语音层后挂断，只按原通话的回执结算；交接时已没有有效通话，则落库后通过飞书后台发送全文。CLI 超时只影响发送结果。旧通话的迟到转写和输入信号不影响新通话。
- 已接通的通话结束只记录状态事件；若随其他消息一起放行，保持到达顺序并在同次模型请求中可见。响铃后未接通或仅解除本地音频绑定都不记录结束事件；已接通窗口被确认消失才记录。
- 调度器拦截和语音层停播通过同一接口返回回执，分别确认零投递和已播前缀（没有已播正文时也为零）。模型发出首段文字后一直等待时，提前返回非完整回执即可截断模型流，无需等待下一个片段。
- 非完整回执只结束本轮：已启动的工具和确认的正文照常落库，不进入工具续轮；已有队列消息可立即开始下一轮。即使模型先结束、回执后到，这条规则也成立。
