首版在同一台 Mac 上通过两条独立的本机虚拟音频线路直连飞书桌面端，自研实时语音处理、Agent 运行时与消息链路。首版用飞书作为唯一界面，服务一个人。通话、文字、图片和语音条进入唯一的主 Session；受委派的子任务在各自的子 Session 中异步执行，历史独立保存。飞书通话挂断不会重置主会话历史，日后更换客户端也不必重写 Agent。

# 首版范围与可行性

专用飞书账号只与本人交互。首版不做独立界面、多用户或多个面向用户的主会话；支持一个主 Session 和多个异步执行的子 Session。首版不部署 LiveKit Server，不建 LiveKit 房间，也不使用 RTC 音频桥。LiveKit Agents SDK 的源码用于参考实时语音逻辑，不作为首版运行时依赖。

\*\*已有验证：\*\*此前已在本地跑通 LiveKit Server 和 LiveKit Agents 官方 Demo，实时语音与文字可交替使用；也验证过飞书窗口状态监听与自动接听、旧方案通过两条虚拟音频线路进行双向通话，以及用飞书 CLI 以用户身份收发消息和媒体。这些是历史验证；首版去掉 RTC 之后的本机直连尚未实测。 窗口监听和自动接听是旧验证，不纳入首版实施。

\*\*可行性结论：\*\*同机直连不需要把音频绕经 LiveKit 房间。飞书负责其已有的降噪，自研实时语音组件参考 LiveKit Agents SDK 的实现。现有调研未发现自研主链路必须依赖闭源组件；本机直连和具体设备组合仍待实测。

# 分层与职责

## Python 单进程

首版用一个 Python 进程运行。通道接入、实时语音和 Agent 运行时按模块分层，通过进程内接口交换文本、事件和音频，不引入进程间通信。网络收发用异步任务；播放回调只按设备需要从语音队列取帧，不等待网络或执行识别、合成等耗时工作。这样既保留了可替换的模块边界，也不必为了分层多部署一套进程。

## 通道接入层

飞书适配器负责使用飞书 CLI 收发消息和获取媒体。运行时把主 Session 的对外回复文本流交给通道，通道只按启动配置选择文字或实时语音，不读取飞书的实际接通状态。实时语音组件是通道可选用的能力，不是横在所有通道和运行时之间的一层。以后增加其他 IM 或自研客户端时，替换平台适配器即可。

**首版通道模式由启动配置指定。**`voice` 模式启用本地双向实时音频，把主 Session 的所有对外回复交给实时语音组件播报；`text` 模式不启用实时音频设备，把对外回复通过飞书 CLI 发送为文字。两种模式都保留飞书 CLI 消息轮询、图文和语音条输入。用户通过修改配置并重启服务切换模式，实际通话由用户在飞书桌面端手动接听和挂断。首版不做窗口识别、自动接听或挂断，也不根据通话状态自动改走文字。两条输出路径仍沿用各自的投递确认规则。

**音频 I/O 适配器**是通道接入层的组件。首版在同一台 Mac 上使用两条独立的虚拟音频线路：一条把飞书扬声器输出送到程序输入，另一条把程序输出送到飞书的虚拟麦克风。模块只读写系统音频设备，不判断音频来自飞书还是其他 IM；通用语音逻辑也不依赖飞书或具体虚拟声卡；未来有需要可以增加 WebRTC 适配器，而不改 Agent 运行时或重写语音处理。具体接口方法留到实现阶段。

## 可复用的实时语音组件

通道通过进程内的标准双向音频接口使用实时语音组件。设备在启动时分别声明输入和输出的采样率、声道数与样本格式，语音组件校验后才开启流；不要求两路使用同一采样率，不在每帧重复传递格式。组件负责 ASR、话轮结束判断、回复切段、TTS 调度、播放以及打断；通道负责设备连接、输出路由，并把交付结果统一回传给运行时。

\*\*音频格式适配：\*\*输入在提交 ASR 前直接按接口要求适配，并将需封装的音频整理成受支持的文件格式；不先统一到一个中间采样率。输出把带格式信息的 TTS PCM 交给支持重采样的系统播放接口，按需由系统转换，应用不重复转换。

## 自研 Agent 运行时

运行时接收文字和图片，负责模型访问、工具调用循环、输入队列、异步子任务、各 Session 的历史与上下文，向通道输出主 Session 的回复文本流。它接收通道的统一交付结果，但不接触音频，不判断通话状态，也不需要区分是语音播完、打断，还是文字发完。工具的具体业务由自研程序负责。

\*\*工具接口与注册：\*\*工具统一声明名称、描述、参数格式和执行函数。首版在代码里用固定列表静态注册：运行时根据列表向模型声明可用工具，收到工具调用后交给对应的执行函数。新增工具遵循同一接口，不引入动态发现、插件加载或完整工具目录。

## 异步子任务

首版完整实现委派、异步运行和结果投递。主 Session 调用委派工具后，立即取得可再次调用的子 Session ID 和标识本次执行的运行 ID。工具的即时返回是委派已受理，不是子任务结果；主 Session 不等待子任务结束，可以继续接收和处理用户消息。同一子 Session 再次被调用时，使用原来的子 Session ID 和新的运行 ID。

委派是首版唯一的业务工具，只负责提交任务，不单独设置工具超时。提交出错时，记录失败，并将明确的失败结果关联原工具调用 ID 落库、回传给模型；Runtime 不等待未受理的任务回投。单主会话最多同时执行 2 个子任务，已受理未结束的任务最多 8 个；超额按原工具调用 ID 返回失败，不创建任务。

子任务独立执行并保存自己的历史。任务完成并落库后，将结果连同子 Session ID 和运行 ID 投递到主 Session 的队列，不把子 Session 的完整执行过程写入主历史。主 Session 正在运行时，结果在下一处安全边界纳入；主 Session 空闲时，结果入队后立即触发一次新运行。子任务结果是内部输入，不直接走飞书或语音投递，也不改变主 Session 对外回复的交付确认规则。

首版不允许只由后台回投触发、且尚未纳入新用户输入的运行再次委派；若同一运行在安全边界纳入了用户输入，则可正常委派。被拒绝的委派仍按原工具调用 ID 记录和回传失败。

终态写入可有限重试，不重跑模型，写入成功后才回投；持续写失败时记录诊断，不伪造终态或回投。退出开始时同步停止接收新委派和新回投；已入队不代表已消费，首版不恢复未完成任务，也不重放回投。

## 模型能力与供应商适配

ASR、LLM 和 TTS 各有独立接口和各自的供应商适配器，可通过配置更换实现。实时语音组件调用 ASR 和 TTS；飞书通道转写语音条时调用同一 ASR 能力，但不经过实时话轮或打断逻辑；Agent 运行时调用 LLM。自动故障切换不纳入首版，留待后续。模型接口不绑定飞书、音频设备或特定供应商协议。

\*\*首版 LLM：DeepSeek。\*\*只实现一个 DeepSeek 适配器。参考 [Agent Workbench 的 DeepSeek 适配器](https://github.com/nickham-su/agent-workbench) 的接入、请求参数和工具调用消息处理方式。开发时以 [DeepSeek 官方 API 文档](https://api-docs.deepseek.com/api/create-chat-completion/)核对最新适用型号及流式输出、工具调用、[图片输入](https://api-docs.deepseek.com/guides/vision/)的支持，不直接照搬参考仓库的型号和参数。

**模型请求配置。**DeepSeek 思考模式可配置，默认显式关闭。开启时，按[官方协议](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode)保留并回传所需的原始 `reasoning_content`，只用于构造模型请求，不进入对外正文、日志或压缩摘要。由关闭切到开启时，待投影的历史若缺少必需字段，用摘要承接不兼容的历史，不伪造字段或改动历史原文。单次模型请求的总时限默认 60 秒，可配置，从发起请求到响应流结束。

\*\*首版 ASR 和 TTS：MiniMax。\*\*分别实现 ASR 和 TTS 适配器，不增加其他供应商。ASR 采用 [MiniMax 文件转写接口](https://solutions.minimax.cn/debug/asr)，由自研适配器提交完整音频文件，不依赖 LiveKit 插件，也不使用边录边上传的 ASR。实时通话里的完整文件是一次话轮的录音，不是整通电话；飞书语音条复用同一个适配器。TTS 仍按小段一次提交文本、流式接收音频。

## 代码组织与启动组装

首版按四块组织代码，部署时仍是同一个 Python 进程：

- \*\*通道接入：\*\*放飞书 CLI 轮询和收发、媒体获取及语音条转写编排、启动模式与输出路由、音频 I/O 适配器，以及对 Runtime 的统一交付确认。

- \*\*实时语音：\*\*通过供应商适配器调用 ASR 和 TTS，负责话轮结束与打断策略、切段调度和播放队列。由通道选用，不依赖飞书或 Runtime。

- \*\*Agent Runtime：\*\*放 LLM 适配器、队列、工具调用循环、异步子任务调度、上下文压缩和模型请求投影。Runtime 在收到交付确认后决定写入哪些对外正文、何时取队列继续。

- \*\*历史存储：\*\*提供薄的读写接口及 SQLite 实现，负责按 Session 持久化和查询历史，不负责对话调度或决定何时压缩。

一个启动入口读取配置（包括飞书通道模式），创建 SQLite 存储和各供应商适配器，再组装 Runtime、实时语音组件与飞书通道，把 ASR 能力分别注入实时语音组件和飞书通道，并通过进程内接口接好输入、回复流与交付确认。通道决定怎么发，Runtime 决定何时写历史和推进，存储只执行请求的读写。

# 主消息链路

- \*\*实时通话（`voice` 模式）：\*\*手动接通飞书电话后，飞书扬声器 → 输入虚拟线路 → 音频 I/O 适配器 → 实时语音组件（VAD 判定话轮结束后，提交该轮录音转写）→ 通道 → Agent；Agent 文本流 → 通道 → 实时语音组件（切段、TTS 和播放队列）→ 音频 I/O 适配器 → 输出虚拟线路 → 飞书虚拟麦克风。

- \*\*飞书文字与图片：\*\*飞书通道解析普通文字、独立图片以及同一条富文本里的图文，获取图片资源后，把文字与图片交给主 Session；图片由支持视觉输入的模型处理。DeepSeek 请求正文上限为 40 MiB。模型投影能容纳完整本轮图文时不裁剪；只有发生预算争用才从批次后向前尝试图片，同一条富文本也优先位置更靠后的图。某张图放不下就继续尝试更早的图，不根据“第一张”等文字猜测指代，也不寻找最优组合。投影仍保留原消息和图文顺序、可读省略提示、原文和完整工具组，不拆批、不改已归档历史。回复形式与输入类型无关，只按本次启动的通道模式选择。

- \*\*飞书语音条：\*\*通道侧获取录音并调用同一个 MiniMax 文件转写适配器，转成文本后随同批其他输入投递给主 Session。不需要建立通话，也不触发语音打断。正常处理时每条语音只发起一次转写请求，失败或超时不重试，该条不入队。首次落库前若进程崩溃，重读时可能重新转写；已经落库的失败通知不会补发。无论是 `text` 还是 `voice` 模式，通道都通过 CLI 在原飞书对话发一次文字通知「语音接收失败，请重新发送。」；通知不作为 Agent 回复写入历史。

## 飞书 CLI 轮询与批量入队

首版用专用飞书账号，以用户身份调用飞书 CLI，不采用机器人身份作为消息入口。这样消息收发与桌面端实时通话沿用同一个账号；实时通话仍通过桌面端和本机虚拟音频线路，不经过 CLI。消息列表固定每 10 秒轮询一次，首版不做变速轮询。只接收指定对话中来自用户的新消息，按飞书消息 ID 去重，并按原消息顺序处理。每个数据库只允许一个飞书主 Session 绑定，首次绑定要求全库没有历史或入站状态；绑定包含主 Session ID、指定对话、对端用户与发送账号，不包含 `text`/`voice` 输出模式。归属校验与 schema 迁移在同一事务中完成，拒绝启动不改动旧库，也不创建外部客户端或音频设备。

按[飞书官方消息内容结构](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json?lang=zh-CN)，文字和图片可能作为独立的 `text`、`image` 消息出现，也可能在同一条富文本 `post` 中出现。两种结构都要支持；同一条 `post` 中的文字与图片保留在同一条输入，独立的消息仍保留各自边界。图片资源在通道侧解析、下载。具体桌面端发送操作对应哪种结构，留到目标 Mac 上验收。

同一次轮询拿到的有效新消息先在通道侧完成解析、媒体获取和所需的语音条转写，再把成功处理的消息按原顺序构造成一个数组，一次性追加到主 Session 队列。通道按原处理顺序执行单媒体和同批展开限额，优先保留文字；超限图片用原位置的可读占位代替。入口不为了让较新图片入选而扩大下载；Runtime 的新近优先规则只用于已经通过入口并仍有图片数据的候选。最终模型请求另校验序列化后的正文大小。语音条转写失败只移出该条，同批其他消息照常入队，不等待失败通知发出。主 Session 空闲时只唤醒一次，同批消息一起进入这次运行；忙时整批等待下一处安全边界。不会让第一条先触发模型，而把同批后续消息留到下一轮。

# 流式合成与播放

## 逐段提交文字并流式接收音频

实时语音组件把 LLM 文本流切成可独立合成的小段，每段文字一次提交，音频分块返回。这里的「整段」是一小段准备播报的文字，不是等整条回复生成完再提交。收到首批音频即可入队播放，不必等该段音频收完。切段、每段何时提交、提交多少段都由语音组件决定；TTS 适配器负责供应商协议和音频接收。提交多个段不等于必须开多个连接，连接能否复用取决于供应商协议。

\*\*取舍：\*\*流式返回音频缩短从首段文字提交到出声的等待；明确的段边界也便于按待播时长控制合成，并在打断时把本地已发音频映射回对应文字。双向流式可以让供应商更早接到零碎文字，但会增加送字节奏和音文对齐的复杂度。在按需合成和近似截断的设计下，这点收益不足以引入额外复杂度。本项目不计划扩展为同一次合成中持续追加文字的双向流式接口。

## 待合成文字队列与待播音频队列

语音组件维护两条队列：待合成文字按段排队，返回的音频按播放顺序入待播队列。首段一切好就提交。同一时刻只合成一段；上一段音频流收完、待播时长低于可配置阈值时，再提交下一段，不必等上一段播完。讨论中的 5 秒只用于说明阈值的作用，不是首版默认值。这样既能在播完之前准备下一段，也能减少打断时合成了却没播的音频。

待播主队列在语音组件内，不在设备适配器里。音频 I/O 适配器按设备回调的需求取帧，没有足够帧时补静音。合成返回可以快于实际播放：如果一段 10 秒的音频在 3 秒内收完，设备仍按自己的播放节奏取帧，而不是在 3 秒内播完。

MiniMax 可能在 HTTP 200 下返回 JSON 业务错误。TTS 适配器对这类响应限制读取大小和时间，区分业务错误与异常响应，不记录响应原文；正常流式音频仍逐块交付。

# 输入优先级与打断

\*\*输入合流。\*\*只有实时语音能打断播报。普通文字、图片和语音条转写均可入队，但不抢占。实时语音转写成功后进入主 Session 的输入队列。主 Session 空闲时，新输入立即触发运行；正在运行时，已入队的消息在下文定义的安全边界纳入模型上下文。

\*\*打断检测与话轮结束是两套独立、可替换的策略。\*\*打断策略决定 Agent 正在说时是否停播。首版参考 LiveKit 使用的开源 Silero VAD 做人声活动检测，优先减少误打断，接受短暂的检测延迟。声纹验证不纳入首版，因此首版不区分是不是本人开口。VAD 本身只检测人声活动，不识别说话人。

**话轮结束**决定用户什么时候说完。首版从最后一次检测到人声开始计算连续静默，默认 1 秒，可配置；静默期间再次开口就重新计时。话轮结束后，把该轮完整录音一次性提交转写，成功后将文字入队。打断由本地 VAD 判定，不等待文件上传或转写结果。首版不用 LiveKit 专用话轮模型或云端自适应打断，降噪沿用飞书。

\*\*打断只改变语音投递。\*\*实时语音组件负责停播、抑制当前回复尚未交付的文本、清空未发音频并取消在途 TTS，随后丢弃该回复迟到的音频帧。已经交给设备的少量数据自然送完，不跨层清设备缓冲。Runtime 不读取语音打断状态，也不因打断暂停或取消模型生成、工具执行或工具循环；它只接收通道的文字投递确认。

- \*\*已经在播报：\*\*停播并清掉待播内容，通道立即按已经交给设备的音频确认文字前缀并回报部分投递；此前没有音频交给设备则回报零投递。

- \*\*正在调工具且没有对外输出：\*\*工具照常执行。新语音转写成功后入队；Runtime 不特意等 ASR，在正常安全边界处理届时已入队的输入。

- **旧回复尚未开始播报：**本地 VAD 判定用户开口后，无论用户仍在说，还是已停说但 ASR 尚未返回，语音层都丢弃旧回复的待播文本。未向设备交付任何音频时，通道回报零投递，不等 ASR；ASR 成功或失败都不会恢复这条旧回复的播报。模型生成和工具仍照常执行。

设备流断开或 VAD 推理出错时，停用实时语音：丢弃待上传录音，取消在途实时 ASR 并忽略迟到结果，停用不等待取消清理。当前回复按失败终态结算，保留已交设备的确认前缀。模型、工具、飞书轮询与飞书语音条转写照常运行，不自动切换输出或恢复设备。

# 统一历史与回复确认

所有面向用户的模态共享主 Session 的长期历史。对模型响应中的对外文本，通道通过同一接口回传**回复 ID、投递状态和已确认投递的正文**。正文可以是全部、已发前缀或空。Runtime 只写入确认发出的正文，不把仅生成、仅合成或送达结果未知的内容当作已投递。工具调用与执行结果不走通道投递确认。

- \*\*通话语音：\*\*以本机交给输出设备的音频为准，不等待飞书远端确认。每段关联对应文字和音频时长，记录当前段及本地已发时长。打断时保留已发完的整段；当前段按进度估算文字前缀，能拿到该段总时长就用比例估算，也可参考已完成段的语速；后续未发的段全部不写入。例：20 字对应 10 秒音频，本地已发 3 秒，可估算保留前 6 字。这只是比例示例，不追求字级对齐，约半句偏差可以接受；尚未收齐当前段时的估算细节留待实现。

- \*\*飞书文字：\*\*以飞书发送成功回执为准，不等已读。发送确认适用于模型响应中的对外文本，不取决于这次响应是否还带工具调用。

\*\*明确失败与结果未知。\*\*通道用同一个回执接口结束 Runtime 的等待：发送明确失败时记为「失败」；超时、未能确认最终投递结果时记为「结果未知」，首版不自动重发，以免重复投递。两种情况下，若没有确认发出任何正文，按零投递落库，保留一条正文为空的助手记录；若有已确认的进度，只保留那一部分。投递状态和错误诊断单独记录，不用错误文字替换助手正文。

## 模型响应的安全边界

一次模型响应可以只有工具调用、只有文本，或同时包含两者。工具调用一旦可执行就开始执行，不等文字投递或语音转写；对外文本则独立走通道投递，两条路径可并行。

安全边界是：**模型响应流已正常结束或进入失败终态、本批已执行的工具都有终态结果且已落库、对外文本已按终态回执处理并落库**。只有工具调用时不等文本；只有文本时不等工具；混合响应必须等两边都就绪。终态回执可以是全量、部分、零投递，也可以是明确失败或结果未知；失败或超时不会让 Runtime 继续等回执。

模型响应正常结束且含工具调用时，到达安全边界后把已经入队的新输入纳入当前运行，连同已落库的结果交给下一次模型调用。正常响应只有最终文本时，到达安全边界即结束本次运行；队列已有输入就立即启动新运行，否则回到空闲。ASR 若此时尚未完成，不单独等待，等转写入队再按空闲或运行中的规则处理。这里的队列同样接收异步子任务的结果；子任务仍在执行，不属于该模型响应尚未完成的工具调用，委派工具以返回受理或失败结果为完成。

模型请求断流或超过总时限时，记为失败终态。未收齐的工具调用不执行，也不进入后续模型请求；已启动的调用照常收尾。结束对外文本流，并按终态回执保留已确认正文。到达安全边界后结束本次运行，队列中的下一条输入仍可正常触发新运行。

首版选用本地 SQLite。一个数据库文件即可服务单用户、单进程下的主 Session 和多个子 Session，无需单独部署数据库服务。各 Session 的原文持久保存并可回查；历史查询与组装模型请求使用不同的读取规则。

## 历史存储接口

Runtime 只依赖薄的历史存储接口，读取和写入都明确所属 Session：追加消息、读取尾部或指定覆盖点之后的原文、读取和保存带覆盖点的摘要、按条件搜索历史。上下文预算、切分与摘要合成由 Runtime 管，SQLite 实现只负责实际的读取、写入和检索。

SQL 和 FTS5 都封装在 SQLite 实现内。历史搜索支持把时间范围与关键词条件组合：时间条件筛选消息，FTS5 做关键词检索；中文分词和短关键词的处理留到实施阶段。不做通用数据库框架，也不为首版实现第二套存储后端。

## 各 Session 的线性历史

主 Session 和各子 Session 都有独立的会话标识。所有消息使用同一个全局自增 `message_id`，每条记录带 `session_id`、角色、内容，以及关联工具调用和结果所需的调用 ID。读取会话历史时按 `session_id` 筛选，再按 `message_id` 排序；筛选后的最大 ID 就是该会话的最新消息，不再为每个 Session 分配独立序号或保存消息头指针。不同会话交错写入导致的 ID 间隔不影响会话内排序。摘要按 Session 独立保存，覆盖点是该会话的一条原始消息 ID。压缩不修改、删除或重排原文。

## 尾部保留与模型请求投影

准备正文模型请求时，以上一次成功正文请求报告的输入用量检查上下文预算（包括纯对话）。达到阈值时，按下述投影规则为最近消息保留原文窗口，冻结已投影的旧前缀与上一份摘要，再异步生成新摘要。切分按完整消息块选边界，工具调用及其对应结果不拆开，也不覆盖本轮受保护输入。同一应用实例的所有主、子 Session 共享一份独立后台生成额度，不排队，不占用正文或子任务执行名额；候选按 Session 隔离，短时留在进程内，空闲不写。

只有下一次正文请求即将发出时（首轮，或工具、投递和入库已收口的续轮）才尝试应用已就绪的候选。SQLite 单次比较旧覆盖点并推进到冻结前缀的末尾，只覆盖旧消息，不丢弃生成期间追加的原文。生成中、失败或写入遇锁时，正文不等待，仍用原读快照；如果覆盖点已被其他写入推进，尝试一次不等锁的一致读，用胜出的摘要及对应原文发包。刷新遇锁才保留原快照，不使用落败候选。同一失败前缀短暂退避。此次改动不增加正文重试，也不能保证已超限的请求恢复。

发给模型时先放当前 Session 的最新摘要，再在同一 Session 内读取 `message_id` 大于覆盖点的原文，按 ID 顺序排列。例如主 Session 的摘要覆盖到 ID 90，之后它有 ID 94 和 101 的消息，夹在中间的 ID 97 属于子 Session；主 Session 的请求只使用「摘要 + 94、101」，历史查询仍能读到本会话被摘要覆盖的原文。下一次压缩只重新概括上次摘要和新移出尾部的消息，不反复从头读取所有原文。

\*\*投递记录不是模型上下文。\*\*组装模型请求或生成压缩摘要时，不传投递状态、超时或错误诊断。零投递且没有工具调用的空助手条目从模型上下文略去；如果同一响应还有工具调用，保留助手的工具调用及对应结果，但其正文留空。已有确认前缀时，只将确认部分作为助手正文。

# 已确定的边界

首版主线是飞书接入、同机虚拟音频直连、自研实时语音处理与 Agent 运行时。通话和 IM 消息共享主 Session 历史，异步子任务在独立 Session 中执行并回投结果，通道按启动配置选择回复形式，不识别窗口或自动感知接通、挂断。旧有验证不等于直连、语音条接入或整条自研链路已验证。具体设备与采样率、方法签名、切段规则、待播阈值和非正常流程留到实施阶段。

\*\*开发与交付。\*\*在云端开发环境实施 `agent-companion`，验证不依赖目标设备的部分。完成后交付可下载的代码包和 Mac 实机验收清单。当前不需要创建 GitHub 仓库或配置云端写权限；苏叶可下载代码后在本地提交和推送。

\*\*目标 Mac 实机验收。\*\*苏叶按清单修改配置并重启服务，分别验收两种模式。`text` 模式通过真实飞书账号和 CLI 验收文字回复、图文输入、语音条和同批多消息只触发一次运行，不依赖虚拟声卡。`voice` 模式下由用户手动接听和挂断，验收两条虚拟音频线路双向收发、实时播报、打断与投递确认。首版不验收自动识别窗口、自动接听挂断或运行时动态切换。云端验证不替代实机结果。

## 异步子任务验收

- \*\*主 Session 正在运行：\*\*委派立即返回子 Session ID 和运行 ID；子任务执行期间，主 Session 仍能接收并处理用户消息。子任务完成后，回投结果在主 Session 的下一处安全边界纳入，不打断当前模型响应、工具执行或对外投递。

- \*\*主 Session 空闲：\*\*子任务完成后，结果进入主队列并立即触发新运行，无需用户再发一条消息。

- \*\*两种场景都要核对：\*\*主、子历史各自落库；主 Session 收到的是归属正确的任务结果，能通过子 Session ID 和运行 ID 追溯该次执行。
